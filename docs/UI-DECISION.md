## Resource investigation, 12 November 2026

The official `Microsoft.WindowsAppSDK.WinUI.CSharp.Templates` 0.0.8-alpha WinUI Blank App was generated for comparison. The template's package-install post-actions failed under restricted network access, so it was inspected, not built. It uses the same .NET target, minimum platform version, `UseWinUI`, `XamlControlsResources`, and `InitializeComponent` / `OnLaunched` pattern. It defaults to MSIX tooling, assets and an application manifest; Xplorer currently uses unpackaged self-contained output. The two project configurations are not identical.

A fresh copy of the actual WinUI project and shared sources was built under ignored `obj/resource-investigation/` with the copy target removed. This isolated output contained `Xplorer.WinUI.pri` and SDK PRI files, but no `resources.pri`. It started and all nine UI Automation smoke checks passed against that output on Windows build 26300. The build had two NU1900 warnings because vulnerability metadata could not be fetched; cached dependencies restored. This does not establish why the earlier blank prototype failed, prove all theme resources or visible rendering work, or validate publishing and other Windows versions. The earlier failure was not reproduced under the current conditions. Keep the copy rule until the chosen distribution path is verified on the intended Windows 10 and Windows 11 versions as requested.

Follow-up: nuget.org TCP port 443 was unreachable in the agent's restricted execution environment but reachable outside it. A forced, no-cache restore of the main WinUI project with network access completed without warnings. The repository source was already correct. This does not permanently change the agent's sandbox network policy; future operations may again need network access approval. This follow-up restored the main project, not the isolated investigation build.

Afterward, at the user's request, local Codex configuration was updated to set `sandbox_workspace_write.network_access = true`. The current session still could not reach nuget.org from inside its sandbox. Verify in a new session whether the setting takes effect or a managed permission profile overrides it; use approved network access for restore if necessary.

Microsoft documents both [unpackaged self-contained deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app) and [resource indexing for unpackaged applications](https://learn.microsoft.com/en-us/windows/apps/winui/winui3/localize-winui3-app). These references do not by themselves identify the original failure. Further work: choose and build the actual distribution artifact, inspect resource and theme behavior visibly, run the UI and file-action checks against that artifact on Windows 10 and Windows 11, then remove the copy target only after those checks pass.

## Publish investigation, 12 November 2026

After the session restart, TCP to `api.nuget.org:443` still failed inside the sandbox. A forced, no-cache restore of the main WinUI project with `NuGetAudit=true` and `NuGetAuditMode=all` succeeded without warnings using the network approval mechanism. This does not establish precisely why the sandbox connection failed.

The previously isolated project without the copy target was published as unpackaged, Windows App SDK self-contained x64 Release with `dotnet publish obj/resource-investigation/WinUI/Xplorer.WinUI.csproj -c Release -p:Platform=x64 --no-restore -o obj/resource-investigation/publish`. The build succeeded with NU1900 from the isolated project's earlier cached restore metadata; the successful audited restore above was for the main project. The publish output contained the SDK PRI files but omitted `Xplorer.WinUI.pri`, which existed in the Release build output. The unmodified publish output exited without producing a window. Manually copying `Xplorer.WinUI.pri` from that build output into the isolated publish directory allowed the app to start and all nine existing UI Automation smoke checks to pass on Windows build 26300. No `resources.pri` was present in that test. This identifies a publish-output difference worth investigating, not the cause of the earlier blank prototype failure or a validated deployment fix. The publish directory had 156 files totaling approximately 158 MB before the manual copy; .NET self-contained status and clean-machine prerequisites were not established.

A visible launch produced a window handle after the diagnostic copy, but a desktop screenshot failed with an invalid handle, so visual rendering, themes and contrast could not be assessed. Separate Windows 10 and Windows 11 systems were unavailable. No supported distribution approach has been selected or validated; retain the existing copy target until the requested cross-version distribution and visible checks pass. Investigate why the application PRI is omitted from publish, then test a clean artifact and its prerequisites on both Windows versions. The local Files repository is available for reference; no Files code or assets were copied.
## Publish target comparison and candidate, 12 November 2026

Fresh Release x64 publish directories were built from the main project with its existing copy target and from the isolated copy without it, using audited restores and `--no-restore`. Both builds succeeded without warnings. Both outputs contained the SDK PRI files but neither contained `Xplorer.WinUI.pri` or `resources.pri`. The main project's Release build directory contained both. The unmodified publish output with the existing target failed to create a window in the smoke test: the target runs after Build and writes into `OutDir`, but does not add its output to the publish file list.

The expanded MSBuild project shows that the Windows SDK names the unpackaged project PRI `$(TargetName).pri`; its `_CreateProjectPriFileItem` target is conditioned on `AppxPackage == true`. The WinUI SDK adds its own PRI files as `ReferenceCopyLocalPaths`. In this configuration the generated application PRI is absent from the .NET publish file set. This explains the observed output difference, but does not establish a general SDK defect or the earlier blank-app failure.

For a reproducible isolated experiment only, the copy without the existing target was given the following target; it has not been added to the application project:

```xml
<Target Name="IncludeProjectPriInPublishExperiment" BeforeTargets="ComputeFilesToPublish" DependsOnTargets="Build">
  <ItemGroup>
    <ResolvedFileToPublish Include="$(TargetDir)$(ProjectPriFileName)" RelativePath="$(ProjectPriFileName)" CopyToPublishDirectory="PreserveNewest" />
  </ItemGroup>
</Target>
```

Publishing that copy with `dotnet publish obj/resource-investigation/WinUI/Xplorer.WinUI.csproj -c Release -p:Platform=x64 --no-restore -o obj/resource-investigation/publish-candidate` produced the application PRI without manual copying. All nine existing UI Automation smoke checks passed on build 26300. The candidate is an ignored diagnostic output, not a release. `WindowsAppSDKSelfContained=true` includes the Windows App SDK, but `SelfContained=false` and the runtime configuration requires Microsoft.NETCore.App 10.0; this machine has 10.0.14 installed. Clean-machine prerequisites, Windows compatibility and redistribution remain unverified. Files' local project uses MSIX tooling and is not an equivalent unpackaged configuration; no code was copied.

The accessible environment did not provide a usable desktop screenshot; the earlier visible launch returned a window handle but rendering was not inspected. No separate Windows 10 or Windows 11 test system was available, and `Get-VM` was unavailable. The conditional decision therefore remains to retain the existing target and keep the candidate experimental. On accessible Windows 10 and 11 desktops, first verify the exact SDK/.NET prerequisites, publish a clean artifact, inspect themes and native dialogs, and run smoke and file-operation tests against it before deciding whether to replace or remove the target.
